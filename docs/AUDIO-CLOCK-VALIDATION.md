# 音频主时钟第一批验收

日期：2026-10-16。用户选择保留 Tauri/React，优先稳定性、可维护性和性能，逐步强化媒体内核。本批保留项目/导出权威状态在 Rust，将预览源时间映射与同步策略独立为纯模块，并改进真实 WebView 播放。

当前后端仍为 HTML video/audio。这里的音频主时钟是媒体元素的 presentation time，不是 WASAPI 设备播放位置。本批不宣称已经交付原生播放器、采样级同步或完整 M2 发布验收。

## 实现与约束

- `preview-clock.ts` 统一处理源时间→项目帧映射、同源连续片段判定及校正策略；不操作 DOM、文件、进程或项目状态。
- 预览按活动独立音轨顺序选主，未静音零增益音轨仍参与；无独立音频时跟随可见视频，真实空隙/只有图片时使用单调时钟。
- 主媒体缺失、waiting、readyState<3、seeking 或暂停时冻结播放头并暂停从节点；即使没有 waiting 事件，时间连续 250ms 无进展也进入等待。正常 100ms 时间量化不会误触发；进展恢复后继续。
- 主节点保持 1x；从节点偏差超过 20ms 时以 0.97–1.03 速率温和校正，超过 250ms 才硬定位，未完成 seek 不重复发起；显式 seek/非连续源区间单独处理。
- 同源连续切段保留实际媒体元素，避免每个 clip 都重建解码器。相邻不连续源区间仍复用元素，但必须正确定位。暂停/卸载恢复速率并阻止迟到播放任务恢复旧流。
- `.kaicut v2`、FFmpeg 二进制、Rust 导出规则、UI 布局/样式与编辑快捷键不变；没有逐帧 IPC 像素传输或空壳 native adapter。

## 方法

`pnpm mcp:playback-check` 通过标准 MCP 客户端连接真实隐藏、无焦点、独立配置的 Tauri 实例。生成 610 秒 640×360/30fps 动态 H.264 与 48kHz 单声道节拍 WAV，默认实际经过至少 600 秒，并要求项目推进到 600 秒。素材总计约 104MB；`--fixtures` 可复用，不使用用户媒体。

每约 450ms 读取实际媒体时间、片段身份、主钟类型、缓冲、速率、硬定位次数与 nodeId。开播前 5 秒单独记录；其后至少 90% 样本必须就绪，统计独立映射到项目坐标后的音视频相对时间差，要求 P95 与最大值都小于 30fps 的一帧（33.33ms）。同时核对真实经过时间/项目推进比；所有样本和等待信息保留，不用音频与自身时钟比较制造零误差。

连续播放后，检查暂停 350ms 稳定性、首/中/尾/返回开头的 seek，并运行 14 秒序列：同源连续切段、相邻不连续源入点、无媒体空隙、重新进入媒体、音频尾段、视频尾段。连续切段要求 nodeId 不变且硬 seek 不增加；相邻不连续切段要求 nodeId 不变、硬 seek 增加且源时间正确。边界 ±0.5s 的样本单独汇总，不将它们混同稳定段精度。

## 验收边界和下一步

计数和时钟来自隐藏 WebView，不证明扬声器输出、屏幕呈现延迟、听感或 60fps 交互。单路合成 360p/30fps 也不覆盖 4K、VFR、长 GOP、不同采样率、双音轨混音、设备切换或受限设备。边界暂时未就绪的时长来自轮询估计，不能宣称逐事件精确停顿时间。

下一阶段优先解决已测出的开播/跳源瞬时偏差和媒体激活等待，再独立验证 Windows WASAPI 时间位置、Media Foundation 解码和 D3D 呈现的最小链路，按实际收益接入当前媒体观测/执行位置。数据恢复与磁盘耗尽等稳定性门槛继续保留；不因一次播放测试关闭产品级稳定性目标。
