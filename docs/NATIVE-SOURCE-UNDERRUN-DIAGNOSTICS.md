# 原生源预览音频缓冲耗尽诊断

上批正常控件回归在200ms近片尾段记录一次音频缓冲耗尽，同程序复测通过。旧记录只保留泵送后的时钟和整段计数，不能确定耗尽发生在启动还是中途。本批先增加发生点证据，保持缓冲容量、播放参数、剩余帧判断和零欠载验收标准不变。

## 新增证据

每段单独保留启动与泵送观察：启动前设备padding、已接收采样量、Start调用耗时、首次泵送相对调用开始及返回的间隔。耗尽事件保留发生前的padding、剩余帧、已提交帧、已有待提交片段、源/渲染代次和原始音频时钟。摘要用于运行时状态，详细记录只在段报告中保存。`pendingFrames`表示游标预留片段，不证明对应PCM已经就绪；`startCallScope`明确为`AudioPreviewAdapter::start`，不是单独测COM Start耗时。

记录数量有上限：最多16次启动和16次耗尽，累计数与丢弃数分开；数据不完整不得当作没有耗尽。解码统计读取需要阻塞锁，因此不在播放线程的发生点额外读取，报告说明该项缺失。首泵时间戳取于GetCurrentPadding返回后，包含查询耗时，不能把整个间隔都归因于调度器。耗尽后额外采样一次设备时钟可能影响之后的补给，不能制造已经观察到的首次padding=0；诊断不是零开销或硬实时承诺。

## 本批验证计划

固定三次正常controls流程和两次`underrun-delay`阳性对照。正常流程继续由既有独立验证器按零欠载标准检查，不因新诊断而放宽。对照在尾段已准备好、音频启动后的第一次泵送前，刻意延迟至少三个设备缓冲时长且至少60ms；请求上限250ms，操作系统调度可令实际等待更长。记录明确标为intentional，不作为自然故障复现或真实实时资格结果。

两个对照必须捕获真实设备padding耗尽及对应发生点，随后正常到片尾并释放资源。所有实例都隐藏、隔离，只静音自身音频会话，不操作桌面或系统设备。

## 结果

## 结论与后续

新增证据在明确的首次供音延迟下工作正常；三轮正常运行没有复现上批偶发问题。因此本轮完成的是定位能力和固定样本验证，没有修复一个已证实的自然欠载根因。原失败记录继续有效，不能据此宣布无断音或整体实时资格通过。

后续固定[20 秒跨度序列](./NATIVE-SOURCE-SPAN-STRESS.md)及[59 秒跨度序列](./NATIVE-SOURCE-LONG-SPAN-STRESS.md)各自完成两轮，均未复现自然欠载，旧偶发事件根因仍未确定。59 秒批次另保留初始素材选择超时记录，验证入口增加实际 DOM 导入确认，不把未进入播放的失败计为零欠载。继续扩大分辨率、素材与设备矩阵，保留每次发生点；真实设备拔插、可见画面、听感、跨设备与物理同步仍待单独验收。隐藏运行仍记录WebView内部`Chrome_WidgetWin_0`注销警告1412，未宣称解决。
