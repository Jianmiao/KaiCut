# Windows 原生预览兼容性探针

本轮承接 [受控随机定位验证](NATIVE-SEEK-PROBE.md)，扩大独立后台探针的时间模型覆盖。目标是验证真实可变帧率时间戳、非零视频起点和 AAC 解码后的采样定位；不凭平均帧率推算源帧，不据此宣布通用素材兼容或正式播放器可替换。

## 范围和安全边界

- 使用仓库已审计的 LGPL FFmpeg/ffprobe，保留既有顺序解码与 `indexed-cfr` 路径作回归对照。不下载或替换编码器。
- 仅使用独立、显式运行的探针；不更改 UI、项目格式、MCP 或主应用默认播放路径。
- 本轮专门验证解码器，不创建 GPU 或音频设备，不创建可见窗口，不控制桌面、不录音、不改系统设置。此前真实 WASAPI/D3D 结果不能代替新增素材的设备验证。
- 真实素材矩阵必须由文件元数据、逐帧时间戳及参考内容核实。请求了 B 帧或写了 VFR 文件名，不等于编码结果真的具备该特性。

## 时间模型与实现边界

视频索引扫描实际解码帧的整数时间戳和时基，严格检查递增、记录数量和大小；上限为 100,000 帧及 8 MiB 索引 JSON。扫描子进程沿用 10 秒截止期限，100,000 帧不是长片处理速度承诺。`indexed-pts` 选取目标所属的前一实际展示帧，保留原始源帧编号，再将输入定位后的 RGB 与索引中对应时间戳逐帧核对。平均帧率只作为元数据，不参与目标帧计算。重复、缺失、逆序或无法表达的时间戳须明确失败，不合成时间戳补洞。

报告必须区分源整数 PTS、流起点、首个解码帧起点和归一化时间。输入定位显式使用 `-seek_timestamp 1` 与绝对 PTS 秒数；ffprobe 使用带显式结束位置的绝对区间。非零源起点不能直接当作需要先播放的空白，也不能在输入定位和时间归一化两个阶段重复减去。首帧、帧边界前后、非边界目标和末帧均应与独立顺序参考一致；每段真实帧间距也必须与参考一致。纯时间模型可解析负 PTS，但当前 FFmpeg 输入适配器明确拒绝负绝对定位锚点，不能宣布负起点素材已通过。

AAC 路径先顺序解码到受控格式的 PCM，再按目标采样帧精确丢弃。解码器对 priming、容器 edit list 和 padding 的处理以实际完整解码的 PCM 为参考，不能再按编码包延迟手工减一次。本轮不承诺直接定位压缩音频的速度，也不把顺序丢弃前缀包装成快速随机定位。非零音轨起点、多音轨间偏移、MP3 延迟仍须独立验证。

全 PTS 扫描会增加准备耗时和内存成本。本轮每个新 decoder 都重建索引，扫描前后复查视频大小、修改时间和完整 SHA-256，没有持久化缓存；`indexBuildMs` 包含这两次源指纹、元数据探测和索引扫描/校验，不能作为纯 ffprobe 扫描时间或缓存命中性能。若以后复用索引，源改变后必须拒绝旧索引。8 MiB 是输入 JSON 字节上限，解析对象、索引向量及外部解码进程还有各自内存成本。

## 验收矩阵与证据要求

| 输入特征 | 必须证明 | 当前证据状态 |
| --- | --- | --- |
| 既有零起点 30fps + PCM | 旧路径首帧、采样区间及结束计数无回归 | 1080p/60 秒既有设备流程及 30 秒定位回归通过，使用 `indexed-cfr` |
| VFR | 实际帧间隔至少两种；目标选帧及连续 RGB/PTS 与顺序参考一致 | 零起点和 +2 秒起点各与两种音频组合通过完整解码及三个定位目标 |
| 非零视频起点 | 实际首个 PTS 非零；归一化首帧和后续定位无双重偏移 | 原始首 PTS 30720，归一化为 0；后续定位通过 |
| AAC | 实际编码格式、采样率、声道和 priming 元数据可追溯；所读 PCM 区间与整段参考一致 | 与三类视频组合，完整 480,256 音频帧及三个定位区间通过 |
| H.264 重排帧 | 实际帧型/重排元数据确认 B 帧存在后，才能记入覆盖 | 实际 190 个 B 帧；两种音频组合均通过完整视频解码及三个定位目标 |

每个通过案例保留源文件摘要、实际编码与时间元数据、目标/实际首帧、至少连续数帧的 RGB 摘要、PCM 源偏移与实际区间摘要、索引扫描/decoder 启动/准备阶段耗时，以及队列高水位和资源回收结果。失败案例保留原始报告和 stderr，不靠隐式回退掩盖。后续接入设备的独立验证才评估供音预算、播放时钟、GPU 和呈现。

单元测试验证时间运算和限额；sidecar 参考验证解码内容；真实 WASAPI/D3D 验证管线与回收。三者不能相互代替。离屏 RGB 正确不能证明屏幕呈现流畅或物理音画同步，短片段通过也不代表长时播放和所有媒体格式已通过。

## 已核验的素材和独立命令证据

素材批次位于 [fixtures-e1094d97](../src-tauri/target/native-compat-validation/fixtures-e1094d97-3cd6-4be9-9585-ad190efc5884/manifest.json)，生成器、命令参数、退出结果、源摘要和逐帧参考均保留在同目录。以下是素材及独立命令证据，Rust 管线结果单列在后文：

- 两个 320×180 VFR 文件实际为 239 帧与 240 帧，时基均为 `1/15360`，源首 PTS 分别为 0 与 30720（2 秒）。偏移封装前后的可见末帧数量不同，因此分别建立完整顺序参考，不能假设仅给同一帧表整体加 2 秒。
- 现有 `h264_mf` 生成的 300 帧测试片实际含 190 个 B 帧，可用于重排解码验证；该结论来自逐帧 `pict_type`，不是根据 `-bf 2` 参数推断。
- AAC 是 48kHz 双声道；流元数据 `initial_padding=0`，但首包 PTS 为 -1024，并明确携带 `skip_samples=1024`。末包 duration 为 768，完整解码输出实际为 480,256 个音频帧；不能用流声明的 10 秒推定恰好 480,000 个输出帧。仅检查流级 padding 字段会漏掉实际 priming 信息。
- [定位命令对照](../src-tauri/target/native-compat-validation/fixtures-e1094d97-3cd6-4be9-9585-ad190efc5884/seek-command-evidence.json) 中，3 类视频在 1.510、3.020、7.123 秒处各取连续 3 帧，相对起点与显式绝对时间定位均与各自参考相符。非零起点案例仍需显式处理绝对/相对坐标，不能由这一个容器推断所有起点语义等价。
- AAC 直接输入定位在 1.510、3.000、3.020、7.123 秒处的前 4096 个音频帧均与完整顺序解码参考不完全一致。各目标提前 1 秒预滚的命令结果均一致，但本轮仍采用保守的顺序解码后采样裁切；单个编码样本的预滚实验不是通用快速音频定位保证。
- 该已审计 sidecar 没有 MP3 编码器，本轮没有引入外部 MP3 样本或其他构建，MP3 延迟覆盖保持未验证。

## Rust 解码器矩阵结果

[原始报告](../src-tauri/target/native-compat-validation/batch-7fad728a-ec94-485e-a040-c08b91a80382/run-fc8028c7-fe6b-478a-ae3d-6167c2da8eb5/native-compat-validation.json) 的 24 个案例全部通过。3 类视频 × 2 类音频，每个组合包含一次从起点完整读到 EOF，以及 1.510、3.020、7.123 秒三个定位目标。

6 个完整案例消费 1558 条视频帧记录，分别覆盖各自 239、240、300 帧的完整参考；3 次 PCM 输出均为 480,000 帧，3 次 AAC 输出均为 480,256 帧。18 个定位案例各核验连续 6 帧，共 108 帧，及不少于 4800 音频帧的连续 PCM 区间；7.123 秒因块边界实际核验 5136 帧。所有实际 RGB、整数 PTS、源帧编号和 PCM 摘要均与独立顺序解码参考一致。

本批每会话建索引阶段为 95.80–245.38ms；18 个定位案例从 decoder 启动前计时到首次消费视频帧为 178.33–300.14ms，包含源摘要、元数据、完整索引和进程启动。这是受控 320×180 短片的单批结果，不与上一轮 1080p 无全索引扫描的 30 秒定位混算提速，也不是设备准备或屏幕显示时间。

音频队列高水位为 8 块、视频队列为 4 帧（691,200 字节），符合既有上限；所有 decoder 均完成关闭和子进程回收，最大显式关闭耗时 8.95ms。完整 EOF 案例的三个持续子进程均正常退出 0；短案例主动取消，允许被结束进程返回非零状态，不能把该状态说成自然 EOF。
