# 原生源预览设备与首帧准备取消

本批延续源素材播放器的开发开关，默认WebView和时间线、项目格式与导出保持不变。验证只使用隐藏窗口、隔离应用数据目录和受控素材，音频仅静音自身会话；不操作可见桌面，不修改系统设备。

## 行为边界

准备请求的取消检查从profile探测延伸到解码器创建、设备打开前后、音频适配器和线程调度初始化，以及第一次画面/音频准备循环。取消之后不能发布旧会话为可播放状态，也不能启动它的音频输出。首次准备成功之后解除这次打开请求的取消检查，避免后续普通播放或定位被旧请求代次错误终止。

设备调用不能安全地从外部强行中断。检查点覆盖调用之前和返回之后；若驱动调用本身迟迟不返回，仍需等待它结束，再在拥有资源的线程上清理。本批不承诺卡死驱动的硬退出期限。

初始化失败报告保留已创建的解码进程、实际设备打开情况、停止/释放、读取线程join和进程reap。音频适配器构造失败也必须留下清理证据。运行时等待初始化线程退出并关闭/解绑原生表面；证据不完整时沿用失败token保护，不启动第二个播放器。

## 受控阶段测试

为避免靠概率碰撞到短暂的初始化窗口，测试在真实资源边界设置一个最长10秒的停留点；它只在debug且启用隐藏隔离验证参数时生效。停留循环检查真实请求取消/应用退出状态，收到后沿正常失败清理路径退出。测试记录停留前后的原始状态与请求身份，超时直接判失败。这是受控调度，停留耗时不能称为实际用户取消延迟。

| 场景 | 证明目标 |
| --- | --- |
| device-cancel | WASAPI实际打开后、尚未启动音频时回到时间线，确认解码器和设备清理；重新选B后原生播放恢复。 |
| frame-cancel | 首次真实prepare tick之后、尚未启动音频时回到时间线；取消首帧准备并完整回收，再选B恢复。 |
| frame-exit | 首次真实prepare tick停留期间请求应用正常退出；不先关闭会话、不强杀主进程，由退出门闩等待准备收尾。 |

三个场景各两个独立进程。检查真实设备已打开、音频未Start、匹配requestId、取消原因、线程和子进程结束、sink退役和child/DComp解绑。首个prepare tick可能还没有写入PCM或收到画面，报告保留真实计数，不把一次tick等同于首帧准备完成。退出期间IPC回包若来不及返回，须和实际后台资源已回收分别说明。

## 证据限制与后续

- 两轮设备阶段初始化失败报告没有直接保存profile指纹；独立核验用导入文件字节、探测记录、请求身份和运行前sidecar哈希关联，明确记录`directProfileFingerprint=false`，不补造指纹。
- 进程采样以PID和创建时间识别所有者，可能遗漏短寿命子进程；17条采样拿不到可执行文件路径。回收结论同时依赖原始decoder/probe的join/reap记录，不把采样缺失当作已经释放。
- 受控停留只验证真实资源获得后收到取消的处理顺序，不测自然竞争概率或用户取消延迟。真实设备打开失败若缺少部分资源释放证据，仍会保守地阻止回退并要求重启。
- 六轮仍出现WebView内部`Chrome_WidgetWin_0`注销警告1412；自有资源回收与应用退出正常不表示此警告已修复。失败校验报告保留，最终报告独立核对打开trace中实际存在的requestId/mediaId，并从准备记录核对项目上下文；旧PID在回归中被复用时未强杀进程，也未覆盖旧采样证据。
- 原生提交回调仍在途时的关闭/定位退役已由后续四轮隐藏批次验证，见 [在途提交退役](./NATIVE-SOURCE-INFLIGHT-RETIREMENT.md)。下一步覆盖真实 Stop/Reset/解绑失败和设备拔插；可见画面、听感、跨设备和物理同步继续单独验收，默认WebView播放器不切换。
